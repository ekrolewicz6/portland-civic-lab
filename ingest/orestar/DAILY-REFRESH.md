## When you download an XLSX yourself

Run `npm run orestar:refresh:manual -- '/absolute/path/to/XcelCNESearch.xlsx'` from this checkout. This is the repeatable path for an ORESTAR **ORESTAR Export** workbook, not a command to edit figures by hand. It validates all 45 columns, dates, amounts, subtypes and IDs; compares overlapping rows with the active database; privately archives the workbook by SHA-256; and appends only new transaction IDs. A new possible City matching payor, conflicting amendment, changed existing financial row or unexpected schema stops the promotion for review. Reimporting the same workbook is harmless. Attempts and failures are recorded in ignored `runtime-data/orestar-manual/refresh-attempts.jsonl` so an unresolved export can be retried.

If the importer stops because an incoming record changes one already held, or supersedes it as an amendment, look at each conflict before doing anything else. Adding `--hold-conflicts` to the command imports the rest of the workbook, leaves every existing record exactly as it was, and lists the held records under `heldForReview` in the archive's `audit.json` and in the active manifest's limits. Held records are never applied by this command. Applying an amendment is a separate, reviewed change.

On success the command builds a new immutable DuckDB database, recalculates accounting, source categories, donor record groups, monthly totals, weekly peaks and reviewed matching-payor totals for every reviewed candidate committee, checks them against the underlying rows, then atomically moves the active manifest. Reader-facing profile and race totals, contribution mosaics, the explorer/API and the main page's **Latest reported fundraising** panel query that database on each request. The cumulative chart and its already-reviewed event windows are derived from that same active database when a manual export is newer than the last complete automated chart. There is no daily link to maintain. Keep the local site running with `npm run orestar:preview`; no foreground ORESTAR browser is required for this import.

The command does **not** prove the workbook is a complete current ORESTAR view. A date-limited manual download may miss older-dated filings filed late, deletions or superseded versions. A complete source refresh remains the way to reconcile those. Do not add cash payments to obligations, or infer cash on hand from transaction receipts minus payments without current official opening balances.

Run `npm run orestar:daily` from the project checkout. By default this covers January 1, 2025 through **yesterday in Portland time**. For a supervised backtest, pass `--end YYYY-MM-DD`. The run has four stages:

1. The existing public-search collector downloads contributions and all other transaction families, one request stream and one headless tab at a time. Date windows are split below ORESTAR's 5,000-record export cap. Raw partitions, counts, retries, errors and hashes stay under ignored `runtime-data/orestar-daily/runs/END/`.
2. `analysis/daily_dashboard.py` checks source hashes, ORESTAR's final counts, CSV row widths, transaction and original IDs, date range, transaction families and financial subtypes. A new possible City matching payor blocks promotion pending review. It recomputes all 17 reviewed council committees' cash, nonmatching, public-match, itemized-Individual and unidentified weekly amounts from the **complete current view**, so late filings, amendments and current-version removals are reflected.
3. An immutable chart artifact is written under `runtime-data/orestar-daily/snapshots/`. Only after all checks pass does an atomic `current.json` pointer move. The local `/api/campaign-finance/daily` route checks its checksum and serves precomputed timeline data. The browser makes one request; it never queries ORESTAR. The cumulative chart and its dated-event comparisons switch to the validated snapshot; the old chart remains if the refresh fails.
4. The same complete, count-reconciled exports rebuild a new DuckDB database and its committee, entity, alias, transfer and candidate-fact tables. After hash, ID, schema and candidate-fact reconciliation checks, `active-snapshot-manifest.json` switches the active site views to that database. A failed build leaves the previous active database in place. The two publication pointers are separate; if the database stage fails after chart promotion, the run is marked failed and their dates remain visible rather than silently claiming they agree.

The daily runner logs stage starts, retries, failures and completions to `runtime-data/orestar-daily/events.ndjson`. The collector keeps per-partition manifests and request failures. If ORESTAR changes during a run, the collector records the mismatch and stops; the next daily run or a supervised `--refresh` can reconcile it. Do not launch another ORESTAR collector concurrently or use a visible browser to work around an access rejection.

The first full-period approach favors correctness over minimum source traffic. A filed-date-only append could miss deletions or superseded current versions. A future optimization can use filed-date deltas plus periodic complete reconciliation, but may not claim equivalence until version/removal behavior is verified. Site speed comes from precomputation and immutable, compressed chart responses, not live calls to ORESTAR.

## What updates automatically after source access recovers

- Cumulative candidate cash, nonmatching cash, City matches from previously reviewed payor record groups, and itemized-Individual transaction amounts.
- Seven-day pre/post windows for the **already reviewed** event anchors.
- The chart's snapshot and through-date label.
- The one active transaction explorer database and filtered evidence downloads, candidate-profile transaction facts and race comparisons, and the main page's latest-funding panel. Prior database files are retained as immutable rollback evidence, not exposed as daily pages.

Everything else in the September 27 research edition remains frozen: interpreted event narratives and sensitivity tests, donor dossiers, ZIP/address geography, supplier identity analysis, overlap significance tests, endorsement lists, official account balances, statewide charts, and the written investigation. The cumulative chart's amounts and pre/post windows are current for its existing dated event anchors, but an import does not discover new events or prove a cause. Profile and race **transaction** totals are current; official balances are withheld there until re-reconciled. Other analyses require separate enrichment, review and publication gates. In particular, a new matching-payor identity, race crosswalk, geocode or outside-spending target must not be inferred from the transaction CSV alone. Do not describe the whole report as daily-live.

The active Codex heartbeat named **Daily ORESTAR campaign-finance refresh** invokes the local command daily and reports failures or successful new snapshots. The automation depends on the local host, browser runtime, source availability and this checkout. It is not a production deployment or a server-side cron. A deployed public edition needs a durable background worker and artifact store; a short-lived web request must not run the ORESTAR browser collector. Promote independently rebuilt analytical families after their own checks, without changing the reviewed editorial edition automatically.
